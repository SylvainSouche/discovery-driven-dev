# Objects and relationships

This file defines what objects **mean**. It deliberately does not show the
on-disk frontmatter layout — documenting the file format is precisely the
affordance that let two pilot projects hand-write 436 objects that looked
correct and weren't. `scripts/schema.py` is the format. `scripts/model.py`
is the only writer.

## Types

| Type | Is | Becomes settled when |
|---|---|---|
| `obs` | Something noticed — about the domain, the code, or the discussion | never; it is resolved by a DEC |
| `cand` | A possibility raised, not yet chosen | a DEC accepts or rejects it |
| `ai` | **Introduced by Claude, not the user** | a DEC accepts it — never before |
| `uc` | A concrete thing a user does, end to end | a DEC confirms it |
| `req` | Something the system must do | a DEC confirms it |
| `nreq` | Something it must not do, or an approach rejected outright | a DEC confirms it |
| `dec` | A decision. The only thing that confirms anything | recorded on creation |
| `asm` | Believed true, unverified. Carries a certainty | confirmed or refuted |
| `con` | Externally imposed, not chosen | recorded on creation |
| `impl` | An assertion that code realizes specific objects | verified by `check_impl.py` |
| `test` | A functional check exercising a UC or REQ. Not a unit test | it passes |

There is no `spec` type and no `des` type. Across two pilots the specification
layer expressed itself as `refines` chains between requirements — 56 such edges
against zero SPEC objects. Given the choice between creating a differently
typed object and stating a more precise requirement, the second won every time.

`scn` from v1 is now `uc`.

## The refinement DAG is the specification layer

`A refines B` means A is a more precise statement of B. Chains run deep — the
bmake-it pilot reached depth 9. The structure gives you three things free:

- **Intent** is at the roots: broad statements nothing refines further upward.
- **Specification** is depth: each level adds precision.
- **Implementation anchors** are the leaves: nothing refines them, so they are
  the most specific claims the model makes. `model.py leaves`.

A diamond — two requirements refining toward a common ancestor — is legitimate
and common. A cycle is not, and `check` will find it.

## The nine relationships

Fixed and enforced. Unknown keys are rejected at write time, because an
unenforced vocabulary went from 6 keys in one pilot to 24 in the other,
including `raised_and_deferred`, a single edge doing two jobs.

| Key | Written on | Points at | Means |
|---|---|---|---|
| `decided_by` | anything | `dec` | The decision that authorized this |
| `refines` | `req` `nreq` | `req` `nreq` | A more precise statement of that one |
| `supersedes` | anything | anything | Replaces an earlier object |
| `informed_by` | anything | anything | Background that shaped this |
| `resolves` | `dec` `cand` `ai` | `obs` | Closes that observation |
| `raised_by` | `obs` | anything | What surfaced this |
| `motivated_by` | `req` `nreq` | `uc` | The use case this serves |
| `implements` | `impl` | `req` `nreq` | Code realizes that requirement |
| `verifies` | `test` | `uc` `req` | This test exercises that |

### Two invariants that make it enforceable

**Every edge is written on the newer object and points backward in time.**

**No inverse is ever stored.** `decides`, `refined_by`, `implemented_by` and
the rest are computed by `trace.py` from the forward edges. One pilot stored
both directions and they already disagreed: 82 `decided_by` against 69
`decides`. Two representations of one fact will diverge.

If you want to say "this DEC produced that REQ", write `decided_by` on the REQ.

## Identity

Every object has an immutable canonical id, generated by the script and checked
against the directory before it is accepted. Ids are never reused, even after
an object is rejected or superseded.

An **alias** is an optional human-readable tag, unique among *active* objects
and freely renamable. Aliases exist for people; ids exist for machines.

**Every stored edge points at a canonical id, never an alias.** Renaming an
alias must never break a relationship. Documents generated from the model may
cite aliases for readability — `views.md` covers keeping those honest.

## Provenance is mandatory

`--origin` is required on creation. It was optional in v1 and 163 of one
pilot's 249 objects carry a placeholder saying it was never filled in. That
information is unrecoverable; no tool can reconstruct where a statement came
from months later.

Say what actually happened: `"user statement, 2026-08-29"`,
`"inferred from OBS-<id> during validation"`, `"proposed by Claude, unapproved"`.

## Supersession is total; refinement never invalidates

These are the two ways an object changes, and confusing them is the most
damaging modelling error available.

**Refinement adds precision. It cannot invalidate anything.** `B refines A`
leaves A confirmed and true. So if half of A is wrong, refining it does not
help: the wrong half stays confirmed, stays citable, and keeps appearing in
generated documents as current.

**Supersession is total.** An object is either still true, or it has been
replaced. There is no partial supersession, and no relationship key expresses
one. Both pilots reached for that idea anyway and invented `revises_partial`
and `resolves_partial` — evidence that the need is real and that ad-hoc keys
are not the answer.

When part of a statement is invalidated, there are exactly two correct moves.

### Absorb — one replacement

Use when the surviving part and the changed part do not stand alone. The
replacement restates what was kept and states what changed, as one object.

```bash
model.py supersede --old libs-ordering --decided-by rework-dec \
  --origin "validation finding, 2026-08-29" \
  --with "libs-ordering-v2:LIBS= entries are processed left to right, and unresolved entries are ignored"
```

### Split — several replacements

Use when each part is a coherent statement on its own. Every replacement
supersedes the original.

```bash
model.py supersede --old link-with-macro --decided-by split-dec \
  --origin "validation: header visibility must come from PREREQS" \
  --with "libs-link-only:LIBS= names libraries to link against, link-time only" \
  --with "headers-via-prereqs:Header visibility is determined exclusively by PREREQS"
```

This is the real change a pilot made when `LINK_WITH=` became `LIBS=`: one half
(linking) survived, the other half (header visibility) was wrong. Two coherent
statements, both superseding one.

### What the operation enforces

- A DEC is **required**. Supersession without a recorded decision loses why.
- The original's status becomes `superseded`, automatically.
- An already-superseded object cannot be superseded again.
- Refinement parents are inherited by **following supersession**, not by
  copying a dead pointer. A single heir is followed automatically; a parent
  that was split refuses to guess and prints the commands to choose.
- Children still refining the replaced object are listed immediately, and
  `check` reports `refines-dead` until they are re-pointed.

`check` also reports a `live-superseded` object (something replaced it but its
status says otherwise) and an `orphan-superseded` one (marked replaced with
nothing replacing it).

## Feedback flows in every direction

Downstream work routinely discovers something that changes upstream. Writing a
use case for an existing requirement can reveal three sibling requirements
nobody stated. Implementing a leaf can prove a requirement wrong.

The mechanism is the same whether the discovery happens five seconds later or
three weeks later: create the new object, link it, and if something must
change, record a DEC and supersede. Never silently rewrite a confirmed object —
supersession is visible, editing is not.
